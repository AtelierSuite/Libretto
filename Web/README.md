# Libretto for the web

The offline, installable web version of Libretto: the same Swift engine the Apple apps use (`../Engine`), compiled to WebAssembly, behind a web interface built on the Libretto design system. No Node packages: the build is Swift and a shell script, and the page is plain HTML, CSS and JavaScript modules. It follows Tables' web app (`../../Tables/Web`) file for file.

- [PLAN.md](PLAN.md): the porting plan and where it stands.
- [design/](design/): the design system. Rules are in `design/DESIGN.md`.

## Layout

| Folder | What's in it |
| --- | --- |
| `index.html`, `manifest.webmanifest`, `sw.js` | The page, the install manifest and the offline service worker |
| `app/` | The window: pages, code editor, menus, inspector, files, autosave, strings |
| `engine/` | The engine's WebAssembly interface (Swift), its WASI host, worker and loader (JavaScript), and smoke tests |
| `strings/` | The web app's own string catalogue (`.xcstrings`, five languages), its strings shared with the Apple apps' catalogues |
| `design/` | Design tokens, components, menus, lint and specimen |
| `build/`, `dist/` | Generated by `build.sh`, not checked in: the build, and the site to publish |
| `deploy/`, `wrangler.jsonc` | Publishing to Cloudflare: headers, `robots.txt`, sitemap, the CI build |

## Setting up

The engine builds with the open-source Swift toolchain and its Swift SDK for WebAssembly, of exactly the same version. Xcode's own toolchain can't use the SDK.

1. Install the swift.org toolchain, for example Swift 6.4.2 from [swift.org/install](https://www.swift.org/install/). On a Mac it installs to `~/Library/Developer/Toolchains`.
2. Install the matching Swift SDK for WebAssembly:

   ```sh
   swift sdk install https://download.swift.org/swift-6.4.2-release/wasm-sdk/swift-6.4.2-RELEASE/swift-6.4.2-RELEASE_wasm.artifactbundle.tar.gz \
       --checksum 83baca83553f8c443cda7b84800912e6e709c3acd2e7ebf277794ca5836c0da5
   ```

`build.sh` looks for these at their default locations; set `SWIFT_TOOLCHAIN` and `SWIFT_SDK` to use others.

## Building and running

```sh
./build.sh                # engine, strings and offline file list, into build/
./build.sh --skip-engine  # after changing only the page's own files
npm run serve             # http://localhost:8000 (the specimen is at /design/)
npm test                  # engine smoke tests; pass .docx/.md/.pages/.txt paths to open them too
npm run lint:design       # design rules
```

On `localhost` the offline service worker only installs when the address has `?offline`, so that edits show up without a rebuild. Anywhere else it always installs.

## Deploying

The app is published at [libretto.atelier.ktgk.app](https://libretto.atelier.ktgk.app) as a Cloudflare Worker that serves only static files (`wrangler.jsonc`).

- `build.sh` assembles the site into `dist/`: just the files the page uses, plus `deploy/_headers`. The engine goes up gzipped (`build/libretto-engine.bin`, about 20 MB; not named `.gz`, which Cloudflare answers with a bot challenge) because Cloudflare serves files of at most 25 MiB; the worker decompresses it. `build.sh` stops if any file is too large.
- Every push to `main` that touches `Web/` or `Engine/` builds, tests and deploys through `.github/workflows/web.yml`. Pull requests are built and tested only. The workflow runs `deploy/ci-build.sh`, which installs Swift and its SDK for WebAssembly, builds the site and runs the engine smoke tests. The workflow needs the repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.
- To deploy by hand from a Mac: `./build.sh && npx wrangler deploy`. Wrangler is only the deploy tool, not part of the app.

Visitors pick up a new build the next time they open the app: the service worker installs it alongside the old one and offers to restart.

## How it fits together

- **Engine.** `engine/swift/Sources/LibrettoWasm` links `Engine/LibrettoEngine` (its model and file formats; its TextKit and Core Text layout is Apple-only) into a WebAssembly reactor that exports a few C functions. Requests and responses are JSON, with file contents passed as raw bytes alongside. `WebSession.swift` holds the document and its undo history and makes the edits the Apple apps' text controller makes, on the model directly. `WebRenderer.swift` makes the decisions `DocumentRenderer` and `Typography` make (styles, fonts, colours for light and dark, list labels, table looks, sections, headers and footers) and describes them as blocks and runs for the page.
- **Worker.** `engine/worker.js` runs the engine off the main thread through a small WASI host (`engine/wasi.js`). The engine has no file system and no network.
- **Pages.** `app/pages.js` draws the engine's blocks in one editable flow over a column of pages, moving each block, or each table row, that would cross the foot of a page to the next, and draws headers, footers and page numbers on the pages behind. The browser does the typing; what it changed is read back and sent to the engine as blocks, unchanged ones by ID and the rest as runs naming the inlines they came from, which is how formatting, links, fields, comments and tracked changes the page can't show survive an edit, as the attributed text's boxes keep them on Apple platforms. Places in the text are a paragraph's ID and an offset into it.
- **Code editor.** `app/code.js` edits plain text and source code in a textarea laid over a copy coloured by the engine's `SyntaxHighlighter`, the one the Apple code editor uses.
- **Files.** Files open and save through the File System Access API where the browser has it, and through a file picker and downloads elsewhere. Open documents are autosaved to the browser's private storage, so closing the window loses nothing; Open Recent lists them.
